# Tempo — 自分のペースで、前へ。

行動経済学と行動科学を参考に、**初期設定 → マイルストーンからの予定作成 → 実行記録 → 次の計画の調整**をつなぐ、個人用の予定管理Webアプリです。

PeReduleから着想を得ていますが、画面・データモデル・予定生成ロジックは新しく実装しました。「性格を診断して一律に予定を決める」方式ではなく、本人の希望、作業の制約、確認済みの実行記録を区別します。

## 実装した4つの機能

| 要望 | Tempoでの実装 |
|---|---|
| 初期登録で簡単に個人の傾向を把握 | 6問の短い質問。取りかかり、希望の作業時間、見積もり、締切前の余裕、近い未来と遠い未来の作業選択を保存 |
| 予定・マイルストーン・最終締切から自動配置 | 各区切りの成果、締切、正味作業時間を入力。順序・休憩・空き時間を守った予定案を提示 |
| 予定を入れてはいけない時間の事前設定 | 作業可能な曜日と時間帯、繰り返しの除外時間、日付を指定する固定予定・休暇、1日の上限 |
| 実行記録から個人への調整を更新 | 開始・一時停止・完了・部分完了・延期理由・実作業時間を記録。参考値を再計算し、本人が提案を採用すると以後の予定に反映 |

その他：週間表示、目標ごとの進捗、計画の再作成、固定した作業の保護、直前変更の取り消し、JSONバックアップ／読み込み、利用者ごとのクラウド保存、保存競合の検出。

## 使い方

1. 初回は6問に回答します。回答はあとから「自分に合わせる」で変更できます。未設定のまま閉じた場合は標準設定です。
2. 「自分に合わせる」で、作業可能な曜日・時間、昼休みなどの除外時間、1日の上限を設定します。
3. 「目標を追加」で、最終締切とマイルストーンを入力します。区切りは順番に並べ、各区切りに正味作業時間を設定します。
4. 「最初の一歩」に具体的な行動を、「始めるきっかけ」に行動の場面を任意で入力します。
5. 自動作成された予定案と配置理由を確認して保存します。必要時間が入りきらないときは不足量を表示し、保存を止めます。
6. 「今日の一歩」で開始・一時停止・完了を記録します。タイマーなしの記録も可能です。途中まで進んだ場合は「進めた予定量」を減らして記録すると、続きが残ります。
7. 「ふりかえり」で実績に基づく提案を確認し、合うものだけを採用します。既存の予定を動かす場合は「再計画」の案を確認します。

### 例

最終締切が金曜18時の研究発表なら、「構成を決める／火曜18時／60分」「スライドを作成／木曜18時／150分」「通して確認／金曜18時／30分」と入力します。合計240分の作業量を保ちつつ、短い着手と作業枠へ分割します。昼休み・授業・作業できない曜日を避け、マイルストーンの順序を守ります。

入力した締切は動かしません。その内側に設定する「余裕を残す目標」は柔らかい条件です。目標に収まらなくても本来の締切までに収まる場合は、理由を表示して確認を求めます。

## なぜ、この設計なのか

### 1. 金銭の時間選好を、作業の能力へ直接変換しない

Augenblick, Niederle & Sprenger（2015）では、金銭選択と実際の労力配分で時間不整合の現れ方が異なりました。[1] このため、金銭テストの値から集中時間や必要タスク数を直接決めません。

現在バイアスを表す代表的な枠組みは、概念的には次のように書けます。

\[
U_t = u_t + \beta\sum_{k=1}^{\infty}\delta^k E[u_{t+k}]
\]

ここでβは現在と将来の相対的な重み、δは将来の期間間の割引に関わります。しかし、このアプリの6問や利用ログからβ・δを推定しているわけではありません。仮想的な作業選択にも忙しさ、疲れ、質問理解、予測の誤差などが混ざります。

**実装上の判断**：初期登録は「実用的な設定のための短い質問」です。心理尺度としての妥当性を主張せず、本人が選んだ作業時間や支援の強さを出発点にします。

### 2. 意図を、具体的な場面と行動へつなげる

Gollwitzer & Sheeran（2006）のメタ分析は、行動する状況と行動内容を結び付ける実行意図（if–then plan）を検討しています。[2]

**実装**：「レポートを進める」だけではなく、「夕食後に机に座ったら、見出しを3つ書く」という形を登録し、作業の直前に見せます。

**限界**：この研究はTempoの効果を実証していません。最初の10分という値も、研究から一意に導かれたものではありません。

### 3. 自己設定の締切を増やせばよいとは考えない

Bisin & Hyndman（2020）の実験では、自己設定の締切への需要はあった一方で、その実験条件では締切が完了率を高めませんでした。自己認識や将来予測との関係も検討されています。[3]

**実装**：マイルストーンを本人が編集できるようにし、最終締切、各区切りの締切、余裕を残す配置目標を区別します。前倒しは罰則付きの約束ではありません。失敗を責める点数や連続記録の罰は設けません。

**限界**：この論文から、すべての締切が無効だとも結論しません。支援の適切な強さは、本人の目標や状況によって異なります。

### 4. 計画錯誤への対策として、過去の実績を見られるようにする

Buehler, Griffin & Ross（1994）は、人が課題の所要時間を楽観的に予測する傾向と、関連する過去の経験の使い方を検討しました。[4]

**実装**：確認済みの実作業時間と予定時間を並べ、比率の中央値を参考として表示します。異なる作業を機械的に同じと扱わないよう、次の見積もりへの自動加算は行いません。

**限界**：初版の参考値はカテゴリーをまたいだ集計です。「似た作業なら参考にする」と説明し、同種タスクの厳密な予測モデルだとは扱いません。

## 研究知見と、アプリ独自の設計値

| 内容 | 根拠の位置付け |
|---|---|
| 金銭選択と作業行動を区別する | 実験研究を参考にした測定上の注意 [1] |
| 場面と具体的行動を結び付ける | 実行意図研究を参考にした機能 [2] |
| 自己設定締切の効果を一律に保証しない | フィールド実験を参考にした限界設定 [3] |
| 見積もりと確認済み実績を比べる | 計画錯誤研究を参考にした機能 [4] |
| 最初の10分、1回25分、前倒し1日、余白20％ | 調整可能な製品設計上の初期値。最適値の実証なし |
| 3件から参考値を表示する | 少数の記録で断定しないための実装上の閾値。統計的な信頼性の保証なし |
| 中央値、比率0.75〜2倍、推奨作業10〜60分 | 外れた値を直接反映しないための仮ルール。検証済みの心理モデルではない |

「研究を参考にしたアプリ」と「研究によって効果が確かめられたアプリ」は別です。初版は前者です。

## 初期登録の反映

| 質問 | 保存・反映 |
|---|---|
| 始めるまで時間がかかる頻度 | よくある→早めの短い着手、あまりない→分散、それ以外→標準 |
| 取り組みたい長さ | 15・25・45・60分を初期設定へ |
| 見積もりより長くなるか | 長くなりがち→作業上限の余白25％、それ以外→20％ |
| 締切前に残したい余裕 | 0・1・2日の希望を反映 |
| 今日20分／明日30分 | 回答を別保存。自動診断には使わない |
| 7日後20分／8日後30分 | 上の回答との違いを見直すための参考。自動診断には使わない |

最後の2問は、単独で現在バイアスを識別する尺度ではありません。結果を「先延ばし度70点」のように数値化しません。

## 行動履歴からの更新

- 実作業時間が確認された完了記録が3件以上になると、予定時間に対する実作業時間の比率と作業時間の中央値を再計算します。
- 完了していても時間が未記録なら、その時間を推測しません。
- 実作業が1〜240分の記録を参考値に使用します。長時間の確認済み記録自体は保存できますが、初版の参考値からは除外します。
- タイマーが4時間を超えた場合は、完了時に実際の作業時間を入力して確認します。
- 「取りかかりにくい」と延期を記録した異なる目標が3件以上ある場合、早めの配置を試す提案を表示します。回数をそのまま性格評価にはしません。
- 急用・体調・時間不足・未記録を先延ばしの根拠にしません。
- 推奨値は動的に更新されますが、設定変更は「採用する」を押したときだけです。予定の移動には、別途再計画の確認が必要です。

## 予定生成のルール

実装：`lib/tempo.ts` の `plan()`。外部LLMへの送信は行いません。

1. 完了済み、実行中、一時停止、日時固定の作業を保持します。
2. 全目標のマイルストーンを締切順に処理します。同じ締切では優先度を考慮します。
3. 先行マイルストーンの作業完了予定以後に、後続を置きます。
4. 作業可能な曜日・時間帯から、固定予定、除外時間、他の作業と休憩を除きます。
5. 作業上限に余白率を適用し、1日分の容量を制限します。
6. 1回の希望時間を上限として分割します。短い空き枠も、原則5分以上なら利用します。残りが5分未満の場合はその残量を保ちます。
7. 支援が標準・強めの場合、目標の最初の作業を最大10分へ分けます。この時間は総作業量の内数です。
8. 候補の評価は、日付の早さ、当日の負荷、細かすぎる分割への小さなペナルティで行います。分散・標準・早めで重みを変えます。
9. 余裕を残す目標までに収まらなければ、本来のマイルストーン締切まで探して警告します。
10. なお不足する場合は残量を表示します。部分的な案を「成立した計画」として確定しません。

日時は日本時間（Asia/Tokyo、UTC+09:00）で統一します。初版の探索範囲は今日から180日先までです。

これは説明可能な貪欲法による実用的なスケジューラーです。全組合せを探索する最適化ソルバーではありません。「配置できない」という結果は、このアルゴリズムと現在の制約で案を見つけられなかったことを意味し、数学的な不可能性の証明ではありません。

### 守る条件

- 分割後の正味作業量を保存する。
- 過去に新しい作業を配置しない。
- マイルストーンと最終締切を超えない。
- 固定予定、除外時間、他の作業、休憩と重ねない。
- 完了済みや固定した作業を再計画で失わない。
- マイルストーンの順序に固定作業が反する場合、競合として保存を止める。

## データ・保存・認証

- React / TypeScript / Vinext、Cloudflare Workers / D1を使用。
- Sitesのサインイン済みユーザーIDをサーバー側で取得し、ユーザー単位に保存します。メールアドレスはデータの主キーに使いません。
- 公開時の初期範囲は所有者のみです。共有範囲を変えても、データの読み書きはユーザーIDで分離されます。
- 主要データの保存にlocalStorageは使いません。
- D1の`planner_state`に状態とrevisionを保存。更新時はrevisionの一致を条件にし、別タブの変更の上書きを防ぎます。
- APIで入力の型・件数・ID関係・作業量を検証。認証のない書き込みと異なるOriginからの書き込みを拒否します。
- 保存が失敗した場合は入力中の画面を残し、成功したとは表示しません。
- JSONの読み込みは形式を検証し、置き換え前に確認を表示します。
- Undoは直前の変更1回分です。ページ再読み込み後は保持されません。必要なバックアップはJSONを書き出してください。
- 操作履歴は最新2,000件まで。完了した作業自体は別に保存します。
- 体験モードはサンプルを使った一時的な操作です。サンプルの予定や操作を本人の履歴に混ぜません。

## 開発・検証

Node.js 22.13以上（テストの`node:sqlite`利用には対応バージョンが必要。今回の検証環境はNode.js 24）。パッケージ管理はpnpmです。

```bash
pnpm install --frozen-lockfile
pnpm dev
pnpm exec tsc --noEmit
node --experimental-strip-types --test tests/scheduler.test.ts tests/api.test.mjs
pnpm build
```

D1スキーマを変更した場合は`pnpm db:generate`で新しいマイグレーションを作成します。本番適用済みのマイグレーションは書き換えません。

ローカルD1は、ビルド後に生成される`dist/server/wrangler.json`を指定し、未適用のSQLを順番に適用します。

```bash
node --import ./scripts/sites-env.mjs ./node_modules/wrangler/bin/wrangler.js d1 execute DB --local --config dist/server/wrangler.json --persist-to .wrangler/state --file drizzle/0000_fancy_nuke.sql
```

Sites環境でのプレビュー・公開は、付属のSitesワークフローを使用します。通常の開発環境では、プレビューの保存にはD1とサインインの開発設定が必要です。認証なしの画面は体験モードになります。

## 検証の範囲

- スケジューラーの不変条件、短い空き枠、部分的に保持した作業、タイムゾーンを自動テスト。
- 実際のAPI関数にテスト用の認証プロバイダーとSQLiteを接続し、未認証拒否、保存・読み戻し、revision競合、不正入力、Origin検証、ユーザー分離をテスト。
- 内部プレビューの体験モードで、目標入力→予定案→確定→開始・一時停止→完了記録を操作確認。
- 公開版のChatGPTサインインから保存までの外部経路は、内部プレビューでは再現していません。公開処理の成功確認と、API内部の検証を区別します。
- WebMCP向けに予定読取と目標入力開始の2ツールを実装。今回のブラウザー環境ではツールの登録を取得できず、WebMCP経由の実行検証は未完了です。通常の画面操作に依存しません。

## 初版の限界と次の検証

- 日本時間のみ。外部カレンダー連携、メール／プッシュ通知、複数人の共同編集は未実装です。
- マイルストーンの内容と必要時間は本人が入力します。自然言語から未知の作業を正確に見積もる機能はありません。
- 初期質問は検証済み心理尺度ではありません。行動履歴から個人の経済学的な時間選好を識別していません。
- 参考値は因果推定ではありません。忙しさ、課題難易度、記録の偏りは残ります。
- 部分完了の「進めた予定量」は自己申告です。品質や成果そのものを自動測定しません。
- 固定・一時停止の作業を保護するため、期限や順序に競合が残ると再計画できない場合があります。該当する固定や目標を見直してください。
- 改善の評価では、締切内の達成、着手のしやすさ、予定変更の手間、負担感を合わせて確認します。タスクを細分化して完了件数を増やすだけの評価は避けます。
- 次段階では本人の同意のもと、同じ種類の作業について分散／前倒しの支援を比較し、長期の負担と継続を検討します。現時点でアプリの介入効果は未検証です。
